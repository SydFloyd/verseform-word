# Verseform for Word — System Design

## System shape

Verseform for Word is a pure reference-and-freshness core inside a narrow Office.js shell. Word owns the document canvas. DBS owns authorized Scripture delivery. Verseform coordinates them without copying the document into a second editor or allowing either boundary to define product rules.

```text
Word changed paragraph / annotation event
                │
                ▼
        Office.js Word gateway
                │  paragraph snapshot or user intent
                ▼
       small application kernel
         │                 │
         ▼                 ▼
 pure reference core    DBS scripture port
         │                 │
         └──── plan/result ┘
                │
                ▼
 temporary annotation / optional task-pane preview / guarded Word replacement
```

## Module ownership

```text
src/core/       Pure canon, parser, normalized reference, freshness, insertion plan
src/app/        Closed state/event/effect model, controller, ports, selectors
src/office/     Office.js capability, paragraph, annotation, range, and undo gateway
src/adapters/   DBS JSON transport and local preference/cache implementations
src/ui/         Small task-pane projection of the application view model
tests/          Pure corpus, fake Word/DBS contracts, browser task-pane cases
manifest.xml    Word activation, permission, command, resource, and API requirements
```

A module exists only when it owns a rule or an external adaptation. React and a state framework are unnecessary until the task pane proves complex enough to justify them.

## State tower

The kernel owns one canonical state with five regions:

- **host:** API support, handler generation, active/closed state, last host error.
- **paragraphs:** revision and redacted structural identity for paragraphs currently carrying Verseform annotations; never a persisted copy of document prose.
- **annotations:** annotation ID → paragraph ID, source text, normalized reference, source range, and paragraph revision; the controller owns the enclosing runtime generation.
- **scripture:** catalog, preferred/effective translation, request stamp, bounded preview result, and failure.
- **ui:** pane visibility, selected annotation, optional bounded Scripture preview, and actionable status. Pane visibility controls only hover preview, never detection ownership.

Events describe facts; effects request work. Each shared runtime binds handlers under a monotonically increasing generation and returns a stop handle that removes those exact handlers. Delayed events from a stopped generation are ignored. Paragraph revisions and translation IDs stamp annotation actions; future provider effects also carry their own request generation. Results are ignored unless every applicable stamp still matches.

## Word boundary

**VFW-040 host boundary (2026-09-06):** in Word for Windows 16.0.20326.20132 / WebView2 152.0.4191.66, live observation separates runtime lifetime from native annotation interaction. The same shared-runtime identity survives manual pane close and `Office.addin.hide()`, receives paragraph events, and creates an exact `Created` annotation, but click and `Alt+Down` events remain gated by pane visibility. `D-025` therefore makes **Fill Scripture** the required pane-free command on the ribbon and selected-text context menu. The command reads one Word selection snapshot, resolves exactly one candidate in the pure core, refreshes and annotates that candidate, then reuses the existing DBS/freshness/replacement path. Choosing Fill is an explicit paragraph-end completion boundary; passive detection remains delimiter-gated. Real Word replaced `John 3:16` with NASB and citation while the pane was closed, and one Undo restored it.

WordApi 1.6 provides paragraph-change and paragraph-added events plus stable-per-session paragraph IDs. WordApi 1.7 provides temporary critique annotations plus hover, click, insertion, and removal events. SharedRuntime 1.1 gives one long-lived JavaScript runtime to ribbon/context-menu commands and the optional task pane. **Enable Verseform** completes its Office command event before awaiting idempotent startup. **Fill Scripture** instead keeps its command context alive until it has captured and processed the selection; completing it first can discard the target. **Preview & settings** is a separate manifest-owned ShowTaskpane command. Hiding or closing that pane controls only optional hover preview, never controller lifetime. Annotation click/`Alt+Down` still reuse ready or in-flight preview when delivered, but `D-025` no longer relies on those native events for pane-free operation. Explicit request failure asks the host to reveal the pane and actionable no-change status. WordApi 1.8 popup suggestions remain excluded because Word, not Verseform, owns their replacement. Event handlers are rebound only after a true runtime restart.

The Office gateway retains the event-registration results and an original-context document anchor in a `WordRuntime` stop handle. Startup attempts to clean registrations that were queued before a failure; explicit teardown asks Word to remove every registered handler through that retained context and asks it to clear each controller-owned temporary annotation. Annotation cleanup reports individual failures. While the shared runtime remains alive, a failed cleanup retains ownership, blocks new annotations in that paragraph, and can retry on a later paragraph event; stale or rejected insertion instead reports the cleanup failure and never claims the marker was removed.

`pagehide` cannot prove that an async teardown reaches Word and, under a long SharedRuntime, can accompany optional-pane closure while document event handlers must remain alive. Verseform therefore never invokes teardown from that signal. For actual abrupt runtime loss, VFW-010 keeps a bounded, app-local ownership ledger of at most 256 opaque annotation IDs. Browser ownership mutations use a same-origin `navigator.locks` exclusive transaction that rereads current storage and applies only a delta; the lock never spans a Word call. If locking is unavailable, startup blocks before it binds Word events. Before Word creates a marker, Verseform atomically reserves one bounded opaque slot; after Word returns the ID, it atomically commits that ID before the controller publishes it as actionable. A failed commit triggers immediate exact-ID host cleanup. If the ledger is full, no host annotation is created. Reservations contain only a random opaque token and one-minute expiry, so a crashed pre-create reservation cannot consume capacity forever. A reservation is not an annotation owner record: a crash after Word creates a marker but before the returned ID commits remains an explicitly unrecoverable WordApi 1.7 gap. On every fresh shared runtime, Verseform asks the current document to remove exactly the stored IDs before binding new handlers. Even a successful startup delete keeps its opaque ID, because Word Undo can return it; only a later startup result that says the ID is missing increments its bounded retry count. A missing ID is no longer actionable in that runtime, but is retained for up to eight current-document misses: it may belong to another open document and must be recoverable when that document reopens. A missing sweep never blocks startup. Stop cleans both active and retired IDs from the current runtime without aging them, so closing an unrelated document does not age another document's retained entry. It never enumerates or removes annotations by color, title, range, or nearby prose, and it refuses an unknown ID rather than guessing.

Word on the web has now shown that Undo can resurrect every native annotation from the paragraph state before a replacement—not just the selected annotation—even after the controller asked Word to clear one during its changed-paragraph refresh. While one pane runtime is alive, the controller moves every active annotation affected by a paragraph refresh, replacement, stale rejection, or annotation-removed event into a bounded runtime-only retired map before cleanup. It keeps that opaque ID in the ledger even when the current cleanup says removed or missing. A candidate or a late activation can reactivate it only after `getAnnotationById` proves the same ID is `Created`, in the same paragraph, at the same UTF-16 offset and length, with the same source text. If a late exact resurrection overlaps a newer controller-owned marker, the controller retires and exact-deletes only that newer known ID; cleanup failure blocks the action. The fake-host model proves this same-runtime recovery path, not that Word on the web has delivered every event ordering safely. The controller does not evict a retired ID: capacity exhaustion blocks new markers rather than making an ID Word may resurrect unowned. The retired map contains paragraph/source metadata only in the live task-pane process; it never enters browser storage.

The ledger contains no paragraph text, document name, document identity, account data, or Scripture data. Its browser representation is parsed strictly: malformed roots or entries, duplicate IDs, and overflow leave the existing record untouched and block Word startup rather than silently erasing recoverable ownership. The lock and browser-storage assumptions are local fake/browser-contract evidence only; Word on the web and Windows must still prove them in the intended task-pane engines. On actual shared-runtime destruction, the retired map is deliberately forgotten because persisting its paragraph/source data would violate the local-only metadata boundary. Startup can exact-sweep a stored ID that is present then, but cannot safely map an ID that Word resurrects by Undo after a runtime restart; bounded missing-ID expiry has the same limitation. The new runtime retains only the loaded opaque IDs, so if one later activates it can explicitly say that a previous temporary annotation returned while refusing to guess its range. That makes the post-restart host experiment distinguishable without treating the marker as actionable or deleting it. WordApi 1.7 supplies neither a durable owner tag nor a safe way to distinguish all add-in annotations, so it cannot repair that case by scanning or deleting on appearance. The explicit prior-ID refusal closes VFW-010 under `D-015` without claiming recovery of forgotten paragraph metadata. WordApi 1.7 also does not expose an atomic Word-create-plus-local-commit operation: a crash after host annotation creation but before commit, a corrupted/local-storage collision, or simultaneous commit and host-cleanup failure can still leave an unowned marker that this add-in must not sweep. The reservation and exact-ID retry narrow that window but do not prove it absent. Microsoft documents that hidden listeners in a long SharedRuntime continue running; `VisibilityModeChanged` is only an optional preview policy signal and never owns controller lifetime. These are documented platform limits around a completed walking slice, not claims that Word will deliver or destroy every event ordering.

The Word on the web walk has proved these host facts rather than inferring them from types:

1. delimiter typing yields a changed-paragraph event soon enough for calm feedback;
2. annotation offsets align with the paragraph text returned by Word;
3. click and keyboard activation can identify the exact annotation without mutating prose; and
4. one explicit action can replace that exact occurrence with ordinary Word Undo support, including duplicate references in one paragraph.

The final VFW-010 host pass proved unsupported-host messaging, cross-document operation, pane close/reopen recovery, and a post-close Undo that returned to a current safe preview. The prior opaque-ID refusal remains deterministic proof for the alternate resurrection branch Word did not surface. `D-014` removes hover delivery from the required interaction, and `D-025` removes native annotation activation from the pane-free release gate after the Windows comparison showed it was withheld. Shared-runtime lifetime still does not prove annotation visibility or event delivery, nor recovery of forgotten annotation metadata after destruction; `D-015` owns that refusal. Screen-reader, forced-color, and context-menu operation remain release-host validation. The non-atomic check-then-replace coauthor timing limitation remains accepted under `D-013`.

Verseform maps each background candidate by inserting one critique at a time and recording its returned annotation ID, rather than assuming result ordering for duplicates. Hover/click may select that exact ID when delivered. Fill instead reads the selected paragraph and UTF-16 selection offsets, resolves a containing or immediately preceding local candidate, forces only the paragraph-end completion appropriate to that explicit command, and refreshes the paragraph so no prior event or painted marker is required. Both paths converge before provider access: the controller owns one exact annotation and reloads its paragraph, source range, critique offset/length, state, and owning paragraph before one `Range.insertText(..., "Replace")` mutation. Unknown, missing, stale, changed, and multi-reference selections are refused.

This is the strongest guard the 1.7 surface exposes locally, but it is not an atomic conditional replace: validation and the replace command require separate `context.sync()` boundaries, so a coauthor edit can theoretically land between them. Microsoft’s [Word event matrix](https://learn.microsoft.com/en-us/office/dev/add-ins/word/word-add-ins-events) says `onParagraphChanged` is triggered during coauthoring while annotation click, hover, and removal are not. Therefore annotation events cannot establish an atomic stale guard or close this race; they can only drive local interaction when delivered. Fake-host tests must not be presented as proof that this race is impossible. `D-013` accepts this narrow documented WordApi 1.7 platform limitation: a Word on the web coauthor experiment can reveal behavior but cannot turn the API into a guarantee, and Verseform must not call the interaction atomically stale-safe.

## Detection boundary

The detector consumes plain paragraph text and a canon contract, returning valid and invalid candidates with exact UTF-16 offsets. It knows no Office.js, DOM, provider, translation catalog, or network. Word's `Paragraph.text` omits the paragraph mark, so the gateway separately maps `onParagraphAdded` to the exact preceding paragraph and rereads whether a following paragraph exists. Only that structural proof permits the interaction adapter to append a detection-only newline; a current final paragraph with no typed delimiter remains unfinished.

Verseform's English parser is the initial behavioral reference because it already proves delimiter gating, strict bounds, conservative fuzziness, URL rejection, and false-positive control. DBS's MIT detector is valuable for multilingual book-name data and language patterns, but its DOM transformation, chapter-only/list grammar, direct HTML popup, and unvalidated numeric coordinates do not enter the core wholesale. Any reused DBS code or data is copied locally, audited, corpus-backed, and credited; production never loads the remote detector script.

English behavior is owned by `tests/fixtures/english-reference-corpus-v1.json` plus programmatic coverage of every full canonical name and approved alias in `STANDARD_CANON` version 1. Exact multiword names require real whitespace between their words; only explicitly approved compact aliases omit it. A reference remains unfinished until whitespace or approved closing punctuation arrives. An en/em dash counts as closing prose punctuation only after following whitespace, so typing the same character for a verse range cannot activate early. URL paths/queries, `mailto:`, email-like prefixes, compact identifiers, excluded ranges, and generated citations remain outside detection. Conservative fuzzy matching applies only to capitalized canonical book names, preserves numbered-book ordinals, refuses ties, and never fuzzes numeric coordinates.

The automated performance contract warms the compiled detector and requires each of five scans of a 100,000-UTF-16-unit English paragraph to finish below 250 ms while finding references at the start, middle, and end. Mixed Hebrew/emoji prose around an English reference proves exact JavaScript/Word UTF-16 slicing; it is not a Hebrew-language claim. Existing controller/gateway tests continue to own burst and coauthor-observable paragraph changes, stale-source refusal, duplicate annotation identity, and provider-free detection. Under `D-017`, multilingual parsing is deferred until DBS product review and English-pilot feedback; no additional BrowserBible code or data enters this slice.

## Scripture boundary

The DBS adapter exposes two operations: list authorized translations and fetch one normalized chapter. It validates identifiers before URL construction, uses HTTPS GET only with credentials omitted and no referrer, allows only the `https://arc.dbs.org/api/bible-text/` catalog and encoded translation/book/chapter paths, applies an eight-second timeout, limits catalog responses to 8 MiB and chapter responses to 2 MiB, parses JSON as untrusted input, validates every verse key against the expected DBS section-book code and chapter, normalizes verse text, and selects the requested verse range locally. A DBS singleton empty object is an unavailable chapter, not executable or displayable content. Text normalization collapses provider newlines, repairs glued punctuation boundaries, and removes a conservative trailing title-case section heading; recorded James payload regressions own those rules. BrowserBible's static 66-book section-code table seeded this response boundary and remains credited under its MIT license in `NOTICE.md`; live-payload regressions own verified provider differences, including NASB Hosea's `HS` response prefix instead of BrowserBible's `HO`. No detector runtime or DOM behavior enters the add-in.

Detection never calls this port. Hidden-pane hover never calls it. Optional visible-pane hover or explicit insertion may start a cancellable request; a click reuses an in-flight hover request for the same annotation and translation rather than issuing another. Translation changes, paragraph changes, cancellation, runtime stop, and a different activation invalidate the request stamp, and a result is accepted only when the annotation, paragraph revision/source, translation, and request generation still match. Click-to-insert proceeds only after the bounded passage result is ready and then performs the independent final Word reread and exact range check. If an explicit request cannot load a passage or catalog, the host is asked to show the optional pane with the exact no-change failure. No WEB or other fallback Bible exists.

DBS cache permission is confirmed for this add-in. The VFW-020 browser adapter stores only schema-validated catalog/chapter response bodies in a separate version-one local store: at most 65 entries and 4 MiB total, with a 24-hour catalog TTL and seven-day chapter TTL. Individual responses retain the transport's 8 MiB/2 MiB limits; total-store pruning may therefore decline to retain a large otherwise-valid response without affecting live use. Expired, future-dated, malformed, duplicate, or over-limit state is discarded; quota failures do not block live results; and the task pane exposes a clear action. The translation preference is stored separately and survives a cache clear. Document prose, file/document identity, annotations, accounts, and request history are never cache inputs.

The catalog is the authorization boundary: a passage request is refused until the selected identifier matches a validated catalog entry. The selected saved entry is restored when present; otherwise `ENGNASB`, another unambiguous NASB entry, or finally the first valid catalog entry is selected. The optional task pane shows abbreviation, full title, complete provider notice, and whether a preview came from DBS or local cache. One explicit Word replacement inserts normalized passage plus an editable parenthetical citation; generated citations are excluded from future detection. A full copyright paragraph is not duplicated after each quotation. The pane preserves the provider notice so a writer can apply translation-specific document-level requirements.

## Manifest and hosting

The add-in-only XML manifest requests `ReadWriteDocument`, WordApi 1.7, and SharedRuntime 1.1. It declares one long runtime shared by **Enable Verseform**, **Fill Scripture**, and **Preview & settings**. Fill is an ExecuteFunction control on the Home ribbon and selected-text context menu; Preview is a non-auto-show task pane. No custom shortcut mapping ships until release-host registration is proved. The XML form remains necessary while the unified manifest is preview for production Word add-ins. Development uses a trusted localhost certificate; production substitutes one owner-approved HTTPS origin in all manifest resources.

Only Microsoft's required Office.js CDN and the allowlisted DBS ARC origin are runtime dependencies. The task pane CSP denies all other network destinations. Production hosting may record ordinary HTTP metadata; it must not receive document content and its retention policy must be documented before release.

The task pane declares `color-scheme: light dark` in its document and root CSS, paints its own canvas/text/surface colors for both `prefers-color-scheme` values, and uses paired CSS system colors under `forced-colors: active`. This prevents an embedded Word dark canvas from becoming an implicit text background and preserves the user’s high-contrast palette. A Word on the web dark-theme run showed readable canvas, text, controls, disabled states, and focus after this repair. Structural tests cover both schemes, but Windows forced-colors and screen-reader behavior remain host observations.

## Proof economy

- Pure tests own parser, canon, false positives, delimiters, freshness, and insertion text.
- Fake ports own cancellation, stale results, translation changes, duplicate annotations, provider failures, and cache/storage edge cases.
- Browser tests own the task-pane state and accessibility without pretending to be Word.
- Word on the web owns annotation offsets/events, exact replacement, Undo, task-pane lifecycle, and subscription behavior.
- Word for Windows repeats only the cross-host contract after the online flow is stable.

Every defect leaves a regression at the cheapest layer that can reproduce it. `npm run check` is the repository gate and includes local structural manifest validation. Microsoft's external validator remains a release contract gate rather than a vulnerable build dependency.
